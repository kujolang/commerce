# Optional Square connections

Self-hosted single-merchant deployments may keep a personal access token. Central multi-merchant hosts use `@kujolang/commerce/connections`, the optional PostgreSQL connection store, and `@kujolang/commerce/runtime/connections`.

Inject the OAuth application ID/secret, registered redirect URI, vault and store. `createTokenVault` requires a 32-byte AES-GCM key from your secret manager and a key ID; retain old keys for rotation. Associated data binds ciphertext to canonical merchant/connection/environment identity. Do not store the encryption key in the database. Only the server-side credential resolver returns an access token; browser/status/callback output never includes credentials or refresh tokens.

Authorization uses one-use hashed state tied to the initiating authenticated administrator, merchant and connection generation. The callback consumes state before exchanging the code and verifies granted scopes and provider merchant identity. Lost exchanges require a fresh authorization, not code replay. Reconnection cannot silently bind the same local connection to a different Square seller. Feature-specific scope unions omit fee permissions by default.

Refresh at least every seven days, using `status().refresh_due` to schedule work. The store serializes refresh claims; stale completions cannot replace newer credentials. Unknown refresh outcomes become `reconnect_required`. A process death can leave `refreshing`; after 30 seconds an authorized operator can call `recoverRefresh`, which fences the old worker and requires fresh authorization. Do not delete encrypted records to unblock them. Revocation immediately disables credential resolution. Disconnect attempts remote revocation and retains a tombstone; an uncertain remote outcome stays `revocation_unknown` and blocks reconnection until resolved.

Select a current active location discovered through the connected seller token. Bind that selected location and seller ID into the payment scope, and construct a request-scoped service using the currently resolved credentials. Never cache a service with old credentials indefinitely. Disconnect does not cancel subscriptions, refund payments, or delete historical commercial records. The host must explain those consequences and provide its own approved data-retention/deletion and merchant-support policy.

The supplied HTTP wrapper requires `connections.manage`, an authenticated merchant administrator and same-origin POSTs. Serve production callbacks over HTTPS. The host is responsible for login sessions, rate limits, registered redirect consistency, secret rotation, backup recovery and alerts. The revocation endpoint verifies Square's signature and seller binding; no unsigned event may disable a connection.

Live multi-seller Sandbox OAuth, production account eligibility and Marketplace/commercial approval remain deployment gates. Local encrypted-store and concurrent-refresh tests do not assert approval or production readiness. See [Square OAuth guidance](https://developer.squareup.com/docs/oauth-api/overview) and [refresh/revoke guidance](https://developer.squareup.com/docs/oauth-api/refresh-revoke-limit-scope).
